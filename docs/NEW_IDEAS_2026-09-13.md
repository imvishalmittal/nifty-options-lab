# New ideas — 13 September 2026

Status: candidate research hypotheses. **Nothing in this document has been
backtested, coded, or run.** Every rule below must be frozen exactly as
written — thresholds, windows, and gates decided in advance — before any
discovery run is opened, per this project's standing promotion policy
(`STRATEGY_SPEC.md`). This document does not authorize discovery, paper
trading, or live trading of anything described here.

## Why these two ideas, not a new signal

A review of every completed backtest in this project's ledger — the
original `STRATEGY_STATUS.md` queue, `MORE_IDEAS_RESULTS.md`, and the
newest P1–P7 batch in `NEW_GENERATION_RESULTS.md` — shows the same failure
signature recurring across otherwise unrelated strategies: a positive or
near-positive normal profit factor, undone by a **negative clustered-
bootstrap lower bound and/or heavy concentration in a small number of
trades or years**. P6's premium-stop comparator had PF 2.6 at normal cost,
yet its top 10% of trades supplied 90.22% of gross gains and a single
trade nearly equaled the strategy's entire gross profit. The six-variant
₹180 entry-risk discovery's best configuration had PF 1.003 — a coin flip
surviving on thin margins. The 30-minute opening-range credit spread
passed nearly every gate and failed specifically on sample size and
concentration. P1's futures-trend benchmark failed on drawdown, year
concentration, and bootstrap together.

Every risk control this project has already tried — entry-as-stop,
breakeven-after-favorable-move, stepped trailing stops, maximum initial-
risk caps — attacks the same side of the problem: how much a single trade
can *lose*. None of them address how much of a strategy's total result
depends on a small number of unusually large *wins*. The two ideas below
are aimed specifically at that undiagnosed side, using data this project
already has, rather than proposing another new entry signal into a queue
where the recurring failure has not been about finding a signal.

## Idea 1 — Concentration throttle: reduce position size after a large realized gain

### Objective

Test whether deliberately reducing position size for a cooldown period
after an unusually large realized winning trade changes a strategy's
clustered-bootstrap lower bound and concentration profile, without
changing its entry signal at all. This targets concentration directly,
rather than inferring it only after a full discovery run completes.

### Frozen candidate design

- Apply this as an overlay on top of an **already-specified, already-
  frozen** signal and exit rule from this project's existing queue — do
  not pair it with a new signal. The candidate host strategies, in order
  of preference: the ₹180-touch signal-close-entry family (already has a
  completed discovery result to compare against) and the Retest-15 /
  Previous-day-break family (same reason). Running this overlay on a
  strategy with no existing baseline result would make it impossible to
  isolate what the throttle changed.
- Define a **large-gain threshold** as a realized single-trade net profit
  at or above the 90th percentile of that strategy's own already-completed
  discovery-period trade distribution. This threshold must be computed
  from the discovery-period data only, frozen as a fixed rupee number
  before the throttle rule is applied to any new run, and never
  recalculated mid-run.
- When a trade closes with realized profit at or above that frozen
  threshold, reduce position size (number of lots) by half for the next
  five trading sessions, then return to full size. This is a fixed,
  mechanical rule — it does not depend on any forecast of whether the next
  trade will also be large.
- All other mechanics (signal, entry timing, stop, exit, costs, slippage
  stress levels) remain byte-for-byte identical to the host strategy's
  already-frozen specification. Changing anything else at the same time
  would make it impossible to attribute any change in outcome to the
  throttle specifically.

### What to measure

Compare, against the host strategy's own already-published discovery
result:
- Change in the clustered-bootstrap lower bound (same methodology already
  used elsewhere in this project — monthly clusters, 5,000 resamples).
- Change in top-10%-of-trades gross-gain concentration and largest single-
  year concentration.
- Change in total net P&L and profit factor. A large reduction in total
  P&L alongside a small improvement in bootstrap/concentration would be a
  meaningful, reportable trade-off — not an automatic pass or fail.

### Gates

Do not import a fixed profitability gate from another strategy for this
one. Because the explicit purpose is trading some average return for a
better bootstrap lower bound, the discovery gate for this candidate is:
the clustered-bootstrap lower bound must move from negative to positive,
or if it was already positive for the host strategy, must not become
negative. If the host strategy's own bootstrap lower bound was already
negative and the throttle does not bring it positive, this is a rejection
regardless of any P&L change, since the hypothesis being tested is
specifically about bootstrap robustness, not about maximizing return.

### What this does not do

- It does not modify the host strategy's entry signal, stop, or exit rule.
- It does not apply to any strategy without an existing completed discovery
  result to compare against.
- It does not authorize skipping the host strategy's own already-completed
  rejection — if the host strategy was rejected for a reason other than
  concentration or bootstrap (for example, negative PF outright), this
  overlay is not expected to fix that and should not be tested on such a
  host without saying so explicitly in the write-up.

## Idea 2 — Trade-frequency cap, grounded in SEBI's active-trader finding

### Objective

Test whether capping the number of trades a strategy is allowed to take
within a rolling window — independent of how many valid signals occur —
changes economic outcomes, as a direct test of the one broad, source-
grounded finding in `PROFITABLE_TRADER_PROVENANCE.md`: SEBI's FY22 active-
trader trimmed sample showed only 6% profitable versus 94% loss-making,
with heavy trading activity associated with worse outcomes. Nothing in
this project's queue has tested trade frequency as an independent lever,
separate from signal quality — every rejected strategy took every signal
its rules produced.

### Frozen candidate design

- Apply this as an overlay on the same class of host strategy as Idea 1 —
  an already-frozen, already-tested signal and exit rule, not a new one.
- Define a **frequency cap**: no more than N new entries within a rolling
  20-trading-session window, where N is fixed before the run at a value
  clearly below the host strategy's own historical average trade rate over
  the same window length (compute the host's historical average from its
  own already-completed discovery data, then freeze N at a stated fraction
  of it, for example half — the exact fraction must be written down before
  the run, not chosen after seeing which fraction happens to look best).
- When the cap is reached, **skip** all further qualifying signals until
  the rolling window frees capacity. Do not queue skipped signals for
  later entry, and do not choose which signals to keep by any quality
  criterion — selecting the "best-looking" skipped signals after the fact
  would reintroduce the same look-ahead bias this project's existing
  promotion policy is designed to prevent. If a rule for which signal to
  keep is wanted, it must be a simple, causal, pre-declared tie-break (for
  example, first-come-first-served within the window), not a filter based
  on any measure of expected trade quality.
- All other mechanics remain identical to the host strategy's frozen
  specification.

### What to measure

Compare against the host strategy's own already-published discovery
result: total net P&L, profit factor, clustered-bootstrap lower bound,
concentration, and total trade count. Because SEBI's finding is about
aggregate outcomes for heavy traders, not about any specific strategy
mechanism, a plausible outcome is that P&L per trade improves while total
P&L falls due to fewer trades — this would be a meaningful result to
report explicitly, not something to discard for looking unprofitable in
aggregate.

### Gates

Reuse this project's standard discovery gates for the host strategy family
(minimum trade count appropriate to the reduced frequency, profitability
and PF thresholds, yearly and monthly stability, clustered-bootstrap lower
bound, concentration ceiling) rather than inventing new ones — the
frequency cap is a position-sizing-style overlay, not a new strategy
requiring its own gate philosophy the way Idea 1's bootstrap-specific gate
does.

### What this does not do

- It does not claim SEBI's aggregate cross-trader finding proves any
  causal mechanism for this project's own specific strategies — it is a
  hypothesis worth testing because of that finding, not a conclusion
  imported from it. `PROFITABLE_TRADER_PROVENANCE.md` is explicit that the
  aggregate evidence "supports descriptive comparisons, not causal claims
  about why a trader won," and this idea should be written up with the
  same care if it is ever tested.
- It does not modify the host strategy's entry signal, stop, or exit rule.
- It does not select which signals to skip based on any forecast of trade
  quality.

## Idea 3 — Multiple-comparisons audit of the existing tested queue

### Objective

This is not a new strategy — it is a statistical audit of everything
already tested in this project, using result data already in hand. Across
V2–V11, the six-variant ₹180 entry-risk discovery, the ten-configuration
close-entry suite, the fifteen/twenty-five-configuration profit-only
suite, and the P1–P7 batch, this project has tested well over 40 named
configurations against overlapping data windows. Nowhere in this project's
documentation is there a check on whether the configurations that came
closest to passing did so partly because testing a large number of
variants makes a false near-pass more likely by chance alone — the same
"look-elsewhere effect" that particle physics and clinical-trial
statistics correct for explicitly. Every individual rejection in this
project's ledger looks methodologically sound in isolation; this idea asks
whether the *pattern* of near-misses across all of them together is
consistent with chance or not.

### Frozen candidate design

- Compile a complete list of every discovery-stage configuration this
  project has run to a terminal verdict (REJECTED, REJECT_DISCOVERY,
  VALIDATION REJECTED, DO_NOT_PROMOTE), with each configuration's normal-
  cost profit factor and its stated pass/fail gate results, sourced only
  from already-published results in `STRATEGY_STATUS.md`,
  `MORE_IDEAS_RESULTS.md`, and `NEW_GENERATION_RESULTS.md`. Do not include
  any configuration still awaiting a result.
- Define "near-miss" as a fixed, pre-declared band around each gate's own
  threshold — for example, a profit factor within 0.05 of the frozen 1.20
  minimum used elsewhere in this project, or a clustered-bootstrap lower
  bound within a fixed, stated distance of zero. The exact band width must
  be chosen and written down before counting any near-misses, not chosen
  after seeing how many configurations it would include.
- Count how many of the compiled configurations fall inside the near-miss
  band on any single gate.
- Compare that count against what would be expected under a null
  assumption that each configuration's gate outcome is an independent,
  random draw with no real edge — this requires a stated, frozen
  statistical method for the comparison (for example, a binomial-based
  expected near-miss rate given the band width and the number of
  configurations), decided before the count is compared against it.

### What this produces, either way

- If the observed near-miss count is not meaningfully higher than the
  chance-expected count, that is reassuring evidence that this project's
  existing rejections are individually sound and not an artifact of
  testing many configurations.
- If the observed count is meaningfully higher, the specific
  configurations inside the near-miss band deserve a second look with a
  stricter, multiple-comparisons-adjusted bar — not automatic promotion,
  but a flag for closer inspection rather than being treated as
  individually marginal-but-independent results.

### What this does not do

- It does not re-run any backtest or generate any new trade data.
- It does not itself promote or reject any strategy — it only flags
  whether the pattern of near-misses across the whole queue warrants a
  second look at specific configurations.
- It does not apply a multiple-comparisons correction retroactively to
  change any already-published verdict; any such change would need its
  own separate, explicit decision and write-up.

## Idea 4 — Confirmation between two of this project's own independently-tested signal families

### Objective

Test whether requiring two of this project's own already-tested,
independently-designed signal families to agree on direction, on the same
session, produces a stronger filter than either family alone — reusing
signal infrastructure this project has already built and evaluated,
rather than proposing a new indicator that would simply become another
single signal subject to the same "coin-flip win rate" failure mode
already diagnosed in the ₹180-crossing family.

### Frozen candidate design

- Select two signal families that each already have a complete, published
  discovery result and that produce a clear, session-level directional
  read (CE-leaning or PE-leaning, or no-trade) — for example, the
  ₹180-premium-crossing family (V2's signal specifically, since it is the
  simplest member) and the Retest-15 or Previous-day-break family. The
  exact pairing must be chosen and written down before any result is
  viewed.
- For each session, determine independently what each of the two families
  would have signaled that day (CE, PE, or no-trade) using each family's
  own already-frozen signal logic, without changing either family's
  signal definition in any way.
- The combined candidate trades only when both families signal the same
  direction on the same session. Sessions where the two disagree, or where
  either family alone would not have traded, are no-trade sessions for the
  combined candidate.
- Entry, stop, exit, cost, and slippage-stress mechanics must be chosen
  and frozen explicitly for the combined candidate before any run — do not
  assume either host family's own exit rule carries over automatically,
  since a two-family agreement requirement changes the trade sample enough
  that the choice of exit rule should be stated and justified on its own.

### What to measure

Compare the combined candidate's discovery-period win rate, profit factor,
clustered-bootstrap lower bound, and concentration against **both** host
families' own already-published standalone results, not just against a
generic pass/fail gate. The specific question this idea is testing is
whether agreement between two independently-built signals raises the win
rate meaningfully above either family's standalone rate — if it does not,
that is itself an informative result about whether the two families are
actually capturing independent information or are more correlated with
each other than assumed.

### Gates

Reuse this project's standard discovery gates (minimum trade count,
profitability and PF thresholds, yearly and monthly stability, clustered-
bootstrap lower bound, concentration ceiling). Because a two-family
agreement requirement will produce fewer trades than either family alone,
the minimum-trade-count gate is especially likely to bind — this should be
treated as a legitimate finding (evidence the agreement condition is too
rare to be tradeable) rather than a reason to loosen the sample-size gate
for this candidate alone.

### What this does not do

- It does not modify either host family's own signal, stop, or exit logic.
- It does not assume the two families are capturing independent
  information — that is the open question this idea is designed to
  answer, not a premise it relies on.
- It does not authorize combining more than two families in this same
  design without a separate, explicit specification, since each additional
  required agreement further shrinks the trade sample and changes the
  statistical picture.

## Idea 5 — Open-interest filter at contract-selection time

### Objective

Test whether restricting contract selection to a minimum open-interest
threshold changes outcomes for a strategy that already selects by premium
level or moneyness. This uses data this project already fetches and
stores — Groww's historical option data includes volume and open interest,
and `STRATEGY_RESEARCH_SUITE.md` explicitly reserves this exact idea for
future testing: "Liquidity/OI filters are not retrofitted into V1 after
inspecting its result; any such filter is a separately frozen variant."
As far as this document's author could find, that separately-frozen
variant has never actually been specified or run. This is a materially
cheaper research item than most of this project's blocked ideas (P3, P7,
S1, S3) because it requires no new data vendor — only using a field
already present in data already being pulled.

### Frozen candidate design

- Apply this as an overlay on an already-frozen, already-tested contract-
  selection rule — the ₹180-premium-crossing family's contract selection,
  or the profit-only family's 200-point-ITM selection. Do not pair it with
  a new signal or a new exit rule.
- Define a minimum open-interest threshold at the moment of contract
  selection, expressed as a fixed number or as a fixed percentile of that
  underlying's own contemporaneous option-chain open interest (percentile
  is preferable, since a fixed absolute number would need separate
  recalibration as market-wide OI levels drift over a multi-year backtest
  window). The exact threshold and whether it is absolute or percentile-
  based must be chosen and frozen before any run, not chosen after seeing
  which threshold happens to exclude the worst trades.
- When the selected contract does not meet the threshold, the session is
  a no-trade for the OI-filtered candidate — do not substitute a different
  strike to satisfy the threshold, since that would silently change the
  strategy's premium-level or moneyness targeting, which is a different
  candidate entirely and would need its own separate specification.
- All other mechanics (signal, entry timing, stop, exit, costs, slippage
  stress levels) remain identical to the host strategy's frozen
  specification.

### What to measure

Compare against the host strategy's own already-published result: change
in fill-quality-sensitive outcomes specifically — realized slippage
relative to the frozen stress assumptions, gap-through frequency, and
overall P&L/PF/bootstrap/concentration. Because this filter reduces trade
count by excluding low-OI sessions, report the excluded-session count and
whether excluded sessions were disproportionately winners or losers in the
host's own historical data — this is diagnostic information about why the
filter helps or does not, not itself a gate.

### Gates

Reuse the host strategy's own standard discovery gates. This is a
liquidity-quality overlay, not a new hypothesis requiring its own gate
philosophy the way Idea 1's bootstrap-specific gate does.

### What this does not do

- It does not modify the host strategy's entry signal, stop, exit rule, or
  premium/moneyness targeting.
- It does not substitute an alternate strike when the originally-selected
  contract fails the OI threshold.
- It does not claim OI-based filtering will help before it is tested — it
  is plausible and cheap to test, not assumed to work.

## Idea 6 — BANKNIFTY as its own frozen discovery, not a pooled multi-index rerun

### Objective

Test whether a signal family that has already shown meaningful (if
ultimately validation-rejected) discovery-period performance on NIFTY
behaves differently on BANKNIFTY specifically, evaluated as its own
separate, freshly-frozen discovery rather than pooled together with other
indices the way this project's only existing multi-index attempt (M3) was
structured.

### Why this differs from M3

M3 applied the already-rejected opening-range credit-spread structure
across NIFTY, BANKNIFTY, and FINNIFTY together and reported pooled and
per-index results for a structure with no underlying edge on any single
index — it was rejected everywhere for the same reason. This idea instead
starts from the Retest-15 or Previous-day-break signal family, the
strongest discovery-period performer in this project's entire ledger
(PF above 1.3 at every cost stress in 2020–2024, before failing
validation on NIFTY specifically), and asks whether BANKNIFTY's materially
different volatility and sectoral composition produce a different result
for that same signal logic — evaluated as BANKNIFTY's own standalone
discovery, not blended into a combined multi-index verdict that could hide
an index-specific effect the way pooling did in M3.

### Frozen candidate design

- Reuse the Retest-15 or Previous-day-break signal definition exactly as
  already specified in `PROFIT_ONLY_DIRECTIONAL_SPEC.md`, substituting
  BANKNIFTY spot and BANKNIFTY's own dated weekly/monthly contracts and
  lot size wherever the existing specification references NIFTY. Do not
  alter the signal logic itself.
- Freeze BANKNIFTY-specific execution details before any run: BANKNIFTY's
  own strike interval, its own lot size history (dated, since lot sizes
  change over time — reuse this project's existing dated-lot-size
  convention rather than a single fixed number), and confirm data
  availability and quality for the full intended discovery window before
  committing to it.
- Run BANKNIFTY as its own independent discovery period and report its
  own standalone result — do not pool it with NIFTY's already-published
  result under a single combined verdict.

### What to measure

Compare BANKNIFTY's standalone discovery result against NIFTY's own
already-published Retest-15/Previous-day-break discovery result on every
already-used metric: P&L, PF, win rate, clustered-bootstrap lower bound,
concentration, and CE-versus-PE breakdown (given this project's own
finding that CE and PE behaved very differently for this signal family on
NIFTY, it is a real question whether BANKNIFTY shows the same asymmetry,
the opposite, or neither).

### Gates

Reuse this project's standard discovery gates for this signal family,
identical to those already applied to the NIFTY version, so the two
results are directly comparable.

### What this does not do

- It does not alter the Retest-15/Previous-day-break signal logic itself.
- It does not claim BANKNIFTY will behave better than NIFTY before
  testing — NIFTY's own version of this signal ultimately failed
  validation, and BANKNIFTY could fail the same way.
- It does not authorize extending this to FINNIFTY or any other index
  without its own separate specification, since each index has distinct
  contract, liquidity, and volatility characteristics that should not be
  assumed to transfer from BANKNIFTY's result.

## Idea 7 — Day-of-week filter, found directly in this project's own raw trade data (SUPERSEDED by Idea 8 — see note below)

> **Status update: superseded, not withdrawn.** This idea's core ambiguity
> — whether the observed weakness was a true calendar-day effect or an
> expiry-proximity effect wearing a day-of-week costume — has since been
> resolved by directly computing days-to-expiry against `public/paper/
> trades.json`, which has both a trade date and an expiry date together
> (`profit-only-history.json`, this idea's original data source, does not
> have an expiry field at all). That direct computation is written up as
> Idea 8 below, using a larger, more directly relevant sample (the ₹180-
> crossing family's own 594-row history, rather than a different signal
> family's data) and measuring the actual mechanism instead of a calendar
> label correlated with it. This section is kept as the record of how
> that better-evidenced idea was found, not as a separate candidate to
> pursue on its own — do not specify or run this calendar-day version;
> use Idea 8 instead.

### Objective

This idea did not originate from documentation review like Ideas 1–6 — it
came from directly querying `public/research/profit-only-history.json`,
this project's own 2,182-row trade-level record for the profit-only
directional suite. Grouping the 2020–2024 discovery-phase trades (1,702 of
the 2,182 rows) by calendar day of week shows:

| Day | Trades | Win rate | Average normal P&L per trade |
|---|---:|---:|---:|
| Monday | 343 | 9.3% | ₹1,041.99 |
| Tuesday | 334 | 5.1% | ₹517.25 |
| Wednesday | 338 | 7.1% | ₹534.49 |
| Thursday | 347 | 8.9% | ₹915.74 |
| Friday | 340 | 5.0% | ₹9.86 |

Friday's average P&L is close to zero despite a trade count nearly
identical to every other day — not an artifact of a small sample. This
was checked against the possibility that it is simply the already-known
CE/PE asymmetry showing up sideways: it is not. Splitting the same
discovery-phase data by side and day shows Friday is weak on **both** CE
(₹30,348.84 total across 181 trades) and PE (−₹26,996.31 total across 159
trades, the only negative day/side cell for PE), while Monday is strong on
both sides (CE ₹58,289.37; PE ₹299,114.66). This also holds when computed
across the full file including the validation phase, not only discovery,
so it is not an artifact of the phase split either.

### A specific, unresolved ambiguity that must be settled before this is run

**This data file has no expiry-date field — only calendar dates.** NIFTY
weekly options' official expiry day was Thursday for most of 2020–2024 but
was changed by NSE at least once within or near this window. This means
the Friday-weakness pattern above could be: (a) a genuine day-of-week
effect specific to Friday itself, (b) a same-day-or-next-day hangover
effect from proximity to a Thursday expiry that happens to correlate with
calendar Friday for most of the sample, or (c) some other expiry-cycle
effect entirely. These would call for different filters. Testing a
calendar-day-of-week filter when the real driver is expiry proximity would
produce a filter that looks predictive in this sample for the wrong
reason, and would likely fail to generalize if NSE's expiry day changes
again or if the filter is applied to a different index with a different
expiry schedule.

### Frozen candidate design

- Before writing any further specification, join this project's own
  historical dated-expiry-calendar data (already used elsewhere in this
  project for contract selection) against the discovery-phase trade dates
  in `profit-only-history.json`, and recompute the same day-of-week/win-
  rate/P&L breakdown segmented by trading days' distance to that week's
  actual expiry, not by calendar day-of-week name. Compare the two
  breakdowns directly before deciding which framing (day-of-week or
  expiry-proximity) the filter should actually use.
- Once that ambiguity is resolved, apply the resulting filter as an
  overlay on the Retest-15 or Previous-day-break signal family — the same
  family this data already comes from — excluding trades that fall on the
  weak day-of-week (or weak expiry-proximity bucket, whichever the join
  above supports) rather than proposing a new signal.
- All other mechanics (signal, entry timing, stop, exit, costs, slippage
  stress levels) remain identical to the host strategy's frozen
  specification.

### What to measure

Compare the filtered candidate's discovery-period P&L, PF, win rate,
clustered-bootstrap lower bound, and concentration against the host
strategy's own already-published unfiltered result. Because this filter
is derived by inspecting the host's own historical outcomes by day, this
candidate carries a real risk of in-sample overfitting that Ideas 1–6 do
not share to the same degree — the day/expiry pattern was observed, not
assumed in advance. For this reason, this candidate's discovery result
should be treated with more skepticism than a first-time hypothesis, and
should not be considered validated on the strength of a discovery-period
pass alone; the existing validation-period data (1 January 2025–8
September 2026), already collected in the same file, should be checked
for the same day/expiry pattern as an out-of-sample confirmation before
treating this as anything more than a discovery-stage candidate.

### Gates

Reuse the host strategy's own standard discovery gates. Additionally,
because of the overfitting risk noted above, do not treat a discovery-
stage pass as sufficient on its own — require the same day-of-week or
expiry-proximity pattern to also appear in the validation-period trades
already sitting in `profit-only-history.json` before treating this
candidate as more than a discovery-stage hypothesis.

### What this does not do

- It does not modify the host strategy's entry signal, stop, or exit rule.
- It does not assume the effect is calendar-day-based rather than expiry-
  proximity-based — that is the first thing to resolve, not an assumption
  this candidate is built on.
- It does not treat a discovery-period pass as validation, given that the
  filter itself was derived by inspecting discovery-period outcomes.

## Idea 8 — Days-to-expiry filter, computed directly against the ₹180-crossing family's own history

### Objective

This resolves Idea 7's central ambiguity by measuring the actual
mechanism — trading days remaining until that week's option expiry —
rather than a calendar-day label. It was computed directly against
`public/paper/trades.json` (594 backtest rows for the ₹180-crossing V2/
V3-5/V3-10 family), which carries both a trade date and a `weeklyExpiry`
date, letting days-to-expiry be calculated exactly rather than inferred.

### What the data shows

Grouping all backtest-sourced rows by trading days remaining to that
week's expiry:

| Days-to-expiry | Trades | Win rate | Average P&L |
|---:|---:|---:|---:|
| 0 (expiry day) | 120 | 36.7% | −₹360.26 |
| 1 | 99 | 27.3% | −₹2,747.48 |
| 2 | 42 | 42.9% | +₹445.32 |
| 3 | 66 | 47.0% | +₹2,488.09 |
| 4 | 48 | 47.9% | +₹644.99 |
| 5 | 57 | 12.3% | −₹3,468.75 |
| 6 | 78 | 32.1% | −₹504.62 |

This was checked for robustness before being treated as real: at
days-to-expiry 1, the *median* trade (not just the mean) is −₹5,025.06,
confirming the weakness runs through the bulk of the distribution rather
than being driven by one or two catastrophic outliers. The pattern is
non-monotonic and mechanistically plausible — days 2 through 4 (the
middle of a weekly cycle) are the strongest window, while the expiry day
itself, the day immediately before expiry, and the day immediately after
a fresh expiry begins are all weaker. Elevated gamma and unstable premium
behavior in the final day before expiry is a well-understood mechanism
this project's own `MORE_IDEAS_RESULTS.md`/S3 discussion already treats
as a real risk in other contexts, which makes this pattern more credible
than a purely data-mined coincidence.

### A required caveat before this can be properly specified

V2, V3-5, and V3-10 all fire from the same underlying signal and session,
so multiple rows in `trades.json` on the same calendar date are the same
trading session counted once per exit-rule variant, not independent
sessions — confirmed by repeated identical P&L values in the raw data.
The trade counts above are session-variant-pairs, not a fully independent
sample. Before treating any of the win-rate or average-P&L figures above
as a statistically meaningful sample size, the data must be de-duplicated
to one row per underlying session (for example, using only the V2 rows,
or explicitly averaging across variants per session-date) so that the
days-to-expiry effect is measured against genuinely independent trading
days, not an inflated count from re-using the same session multiple
times.

### Frozen candidate design

- First, de-duplicate the historical data to session level as described
  above, and recompute the days-to-expiry breakdown on the de-duplicated
  sample before finalizing which days-to-expiry bucket(s) to trade or
  exclude. Do not finalize the filter's specific included/excluded days
  from the row-level (non-deduplicated) numbers shown above.
- Apply the resulting filter as an overlay on the ₹180-crossing family's
  already-frozen signal and exit logic (V2 or V3-10) — do not pair it
  with a new signal. A session outside the chosen days-to-expiry window is
  a no-trade for this candidate, with no substitute contract or session.
- All other mechanics (signal, entry timing, stop, exit, costs, slippage
  stress levels) remain identical to the host strategy's frozen
  specification.

### What to measure

Compare the filtered candidate's P&L, PF, win rate, clustered-bootstrap
lower bound, and concentration against the host strategy's own already-
published unfiltered result (V2's or V3-10's existing backtest figures in
`STRATEGY_STATUS.md`). Because, as with Idea 7, this filter was derived by
inspecting the host's own historical outcomes, treat a first discovery
pass with real caution: check whether the same days-to-expiry pattern also
holds in the ₹180-crossing family's separate 2025–2026 paper-trading
session data (`public/paper/sessions.json`) as an out-of-sample check
before treating this as more than a discovery-stage candidate.

### Gates

Reuse the host strategy's own standard discovery gates. Given the
overfitting risk from deriving the filter by inspection, do not treat a
discovery-period pass alone as sufficient — require the pattern to also
appear in the separate out-of-sample paper-session data referenced above.

### What this does not do

- It does not modify the ₹180-crossing family's entry signal, stop, or
  exit rule — only which sessions are eligible to trade at all.
- It does not finalize which specific days-to-expiry to include or
  exclude before the required session-level de-duplication is performed.
- It does not treat a discovery-period pass as validation, given that the
  filter itself was derived by inspecting historical outcomes from the
  same family it will be tested on.
